# Автопилот входящих сообщений Kwork

## Цель

После отправки отклика система должна быстро замечать новое сообщение покупателя, понимать его в контексте исходного проекта и переписки, формировать человеческий ответ и либо отправлять его автоматически, либо передавать пользователю на подтверждение, если ответ создаёт новое обязательство или требует решения владельца аккаунта.

Главный критерий: обычный предпродажный вопрос получает содержательный ответ не позднее 15 секунд после появления в авторизованной сессии Kwork. Повторная обработка одного сообщения и ложное подтверждение отправки исключены.

## Выбранный подход

Авторитетным источником служит текущая авторизованная вкладка Kwork Chrome через CDP. Мобильный push используется как ускоряющий сигнал и средство уведомления, но не как источник текста или состояния.

Альтернативы отклонены:

- запускать обработку только по мобильному push ненадёжно: уведомление может задержаться или не содержать всей переписки;
- опрашивать Kwork отдельным HTTP-клиентом рискованно: часть чата доступна только в активной пользовательской сессии и может менять внутренние API;
- отвечать на каждый входящий без политики риска опасно: модель может изменить цену, срок или объём обязательств без решения пользователя.

## Компоненты

### `kwork_inbox.py`

Работает с уже открытым Chrome через CDP:

- находит или создаёт одну вкладку `/inbox`, не закрывая пользовательские вкладки;
- каждые 2 секунды читает список непрочитанных диалогов;
- открывает только диалог с новым сообщением и извлекает сообщения из `.conversation-message-item`;
- нормализует автора, время, текст, направление и дату;
- строит стабильный ключ `sha256(conversation + direction + date + time + normalized_text + ordinal)` на случай отсутствия публичного message id;
- отправляет подготовленный текст через штатную форму Kwork;
- считает отправку успешной только при одновременном выполнении трёх условий: `/sendmessage` вернул HTTP 2xx, редактор очистился, появился новый исходящий блок с ожидаемым текстом и статусом «Доставлено» или «Прочитано»;
- при неопределённом результате не повторяет отправку автоматически, а помечает попытку `unknown` и проверяет историю повторно.

### `customer_reply_agent.py`

Получает:

- исходное описание проекта и прочитанные вложения;
- цену, срок и название нашего предложения;
- весь доступный диалог;
- последнее входящее сообщение;
- правила аккаунта: полная оплата после выполнения, не обещать невозможное, не уводить общение с Kwork.

Обращается к облачной модели через существующий OpenRouter-клиент. Модель возвращает строгий JSON:

```json
{
  "intent": "technical_question",
  "reply": "...",
  "confidence": 0.92,
  "action": "auto_send",
  "reason": "Обычный вопрос по подходу к выполнению",
  "commitments": []
}
```

Ответ должен быть конкретным для заказа, состоять обычно из 2-6 предложений, отвечать сначала на вопрос клиента, затем снимать главное сомнение и завершаться следующим практическим шагом. Он не повторяет ТЗ, не пишет цену внутри сообщения, не задаёт вопросы без реальной необходимости и не выдумывает опыт, доступы или факты.

### Политика автодействий

Автоматически отправляются ответы с `confidence >= 0.80`, если они:

- поясняют понимание задачи, подход, инструменты или порядок работы;
- отвечают на технический вопрос в пределах исходного ТЗ;
- подтверждают готовность начать и выполнить уже заявленный объём;
- запрашивают один действительно необходимый доступ или материал после согласия клиента.

На подтверждение в мобильное и десктопное приложение уходят:

- изменение цены, срока, способа оплаты или состава работ;
- гарантия результата, которого нельзя проверить заранее;
- просьба перейти вне Kwork, обмен контактами или платёжными данными;
- конфликт, претензия, отмена, возврат или арбитраж;
- передача секретов и доступов;
- низкая уверенность, противоречие ТЗ или запрос, выходящий за допустимую сложность.

Запрещённый ответ не отправляется даже после ошибки модели. Пустой, шаблонный или не относящийся к последнему вопросу текст также блокируется.

## Хранение и идемпотентность

SQLite получает таблицы:

- `kwork_conversations`: username, связанный `lead_id`, URL, время последней проверки и состояние;
- `kwork_chat_messages`: стабильный ключ, conversation id, направление, текст, время, статус обработки;
- `kwork_reply_attempts`: входящее сообщение, текст ответа, решение модели, статус отправки, ошибка и время;
- `kwork_conversation_claims`: краткая аренда на обработку, чтобы процессы `watch` и `mobile-control` не отвечали одновременно.

Уникальный индекс на ключ сообщения и уникальная активная попытка для входящего сообщения исключают дубли после перезапуска. Исходящий текст сначала фиксируется в БД, затем отправляется. Неопределённая попытка сначала сверяется с историей Kwork и только потом может быть повторена вручную.

### Граница локального и мобильного состояния

Локальная SQLite и фактическая история в Kwork являются авторитетом для обнаружения сообщения и подтверждения внешней отправки. Laravel хранит мобильную проекцию диалога, решение пользователя и очередь команд. Мобильное приложение не отправляет сообщение напрямую в Kwork: оно создаёт идемпотентную команду, локальный исполнитель арендует её, выполняет действие в Chrome и возвращает подтверждённый результат.

Существующий семейный чат не используется как транспорт Kwork. Для диалогов создаётся отдельный API-контур, связанный с `kwork_leads.id`:

- `POST /leads/conversations/sync` — идемпотентный upsert диалога, сообщений, черновика и статуса с desktop;
- `GET /leads/conversations` и `GET /leads/conversations/show` — список и карточка для мобильного приложения;
- `POST /leads/conversations/reply/edit`, `/approve`, `/skip` — решение пользователя;
- `GET /leads/conversation-commands`, `POST /claim`, `POST /result` — отдельная очередь исполнителя, не смешанная с командами первоначального отклика.

FCM-событие имеет тип `kwork_conversation` и содержит `event_id`, `conversation_id`, `lead_id` и статус `new`, `reply_ready`, `needs_approval`, `sent`, `unknown` или `failed`. Нажатие открывает конкретный Kwork-диалог. Существующий тип `kwork_lead` остаётся для карточки проекта.

## Поток выполнения

1. `watch` или `mobile-control` проверяет входящие каждые 2 секунды независимо от десятисекундного сканирования биржи.
2. Новое сообщение сохраняется и связывается с лидом по username, названию проекта и системному сообщению об отклике.
3. Агент формирует структурированное решение и проходит детерминированную политику риска.
4. При `auto_send` ответ отправляется и подтверждается по сети, редактору и исходящему сообщению.
5. Результат пишется в SQLite и синхронизируется с backend мобильного приложения.
6. FCM сообщает о новом входящем, отправленном ответе, необходимости подтверждения или заказе.
7. При новом сообщении цикл повторяется с полной историей, но обрабатывается только последний непокрытый входящий блок.

## Интерфейс

В десктопном приложении добавляется вкладка «Диалоги»:

- непрочитанные и ожидающие решения сверху;
- связанный заказ, последнее сообщение и подготовленный ответ;
- статусы «новое», «готовится», «отправлено», «нужно решение», «ошибка»;
- кнопки «Отправить», «Изменить», «Не отвечать», «Открыть в Kwork»;
- переключатель автответов и журнал фактического подтверждения доставки.

В мобильном приложении используется отдельный структурированный Kwork-диалог: push открывает карточку, где можно изменить и подтвердить ответ. Потеря push не теряет сообщение, потому что приложение синхронизирует Laravel-проекцию, а реальный результат отправки подтверждает локальный исполнитель по истории Kwork.

## Ошибки и восстановление

- Потеря CDP или авторизации: автответы приостанавливаются, пользователь получает push и видимый статус; сканирование публичных заказов продолжает работать, если возможно.
- OpenRouter недоступен: сообщение сохраняется и повторяется с экспоненциальной задержкой; шаблонный ответ не отправляется.
- Kwork вернул 2xx, но исходящий блок не найден: статус `unknown`, повторная отправка запрещена до повторного чтения диалога.
- Страница изменила селекторы: extraction health-check блокирует отправку и пишет диагностический снимок HTML без секретов.
- Два процесса увидели сообщение: обработку получает только владелец действующей SQLite-аренды.

## Тестирование

Unit-тесты:

- извлечение входящих и исходящих блоков из сохранённого HTML;
- стабильные ключи и дедупликация после перезапуска;
- классификация безопасных и рискованных ответов;
- блокировка цены, лишних обещаний, внешних контактов и нерелевантного текста;
- строгий парсинг JSON модели;
- отправка не считается успешной без каждого из трёх подтверждений.

Интеграционные тесты с поддельным CDP:

- новое входящее создаёт ровно одну попытку;
- безопасный ответ отправляется один раз и получает `delivered`;
- таймаут после HTTP 2xx переходит в `unknown`, а не отправляет дубль;
- `watch` и `mobile-control` конкурируют за одно сообщение без двойного ответа;
- рискованный ответ публикуется в мобильный backend и ждёт подтверждения.

Ручной smoke-тест проводится на тестовом или текущем диалоге без повторной отправки старых сообщений: обнаружение, генерация, preview, подтверждённая отправка одного нового ответа и получение push.

## Развёртывание

Функция вводится поэтапно:

1. `observe`: только чтение, запись и уведомления;
2. `approve`: генерация с ручным подтверждением;
3. `auto`: автоматическая отправка только разрешённых категорий.

Для текущего аккаунта целевой режим `auto`, но первые три новых диалога проходят с дополнительным логированием и строгой проверкой доставки. Значения режима, интервала, порога уверенности и лимита ответов задаются через `.env` и интерфейс.
